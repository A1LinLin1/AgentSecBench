# Reproduction-confirmed ground truth protocol

This document defines the evidence set that should be treated as ground truth in
the paper.  Single-reviewer labels and model labels are not considered ground
truth.

## Principle

We separate two claims:

1. **Reproduction-confirmed security behavior**

   A security-sensitive behavior/path is confirmed by a local runtime proof,
   runtime stub, monkeypatch observation, source-level trace, or boundary
   analysis.  This supports evaluation of Security-ADG behavior discovery.

2. **Reproduction-confirmed vulnerability**

   A stricter subset where both impact and trust/auth boundary are confirmed.
   This supports vulnerability-level claims and CVE-oriented reporting.

This prevents intended features, guarded behavior, tests, and source-only traces
from being incorrectly counted as vulnerabilities.

## Inclusion criteria

A record enters `behavior_ground_truth=true` when:

- the evidence status is confirmed; and
- the record does not depend on human/model labels; and
- the record documents at least one source, runtime, stub, monkeypatch, marker,
  or boundary/reachability proof.

A record enters `vulnerability_ground_truth=true` only when:

- confirmed impact evidence exists; and
- a trust/auth boundary is confirmed; and
- the evidence does not explicitly state `not_a_vulnerability_claim=true`.

Confirmed behavior is therefore broader than confirmed vulnerability.

## Coordinate policy

Graph-construction evaluation requires a source coordinate.  The GT builder uses
the following conservative order:

1. `candidate_file` + `candidate_line` from any evidence record grouped under
   the same GT id.
2. A representative coordinate from `candidate_files` + `candidate_lines` for
   aggregate reproduction records.
3. If an evidence record contains an observed effectful call line such as
   `subprocess_run_call_ast.line`, the graph finding uses that
   `evidence_operation_line` while retaining the original `candidate_line`.

This keeps the reproduction case as the unit of ground truth while using the
most precise available line for Security-ADG construction.

## How to use in the paper

Use the reviewed/adjudicated sample only as diagnostic evidence, e.g.:

> We use single-reviewer adjudication for error analysis and method iteration,
> but not as ground truth.

Use this reproduction-confirmed dataset for main evidence, e.g.:

> Our primary ground truth consists of locally reproducible evidence records.
> We distinguish confirmed security-sensitive behaviors from confirmed
> vulnerabilities; vulnerability claims require both impact reproduction and a
> confirmed trust/auth boundary.

Recommended experiment split:

| Evidence source | Role |
|---|---|
| microbenchmark oracle | controlled graph-construction oracle |
| mutation oracle | controlled dependency/guard oracle |
| reproduction-confirmed behavior GT | main real-world behavior evidence |
| reproduction-confirmed vulnerability GT | vulnerability/CVE-level evidence |
| vulnerability disposition matrix | conservative claim boundary and negative-control evidence |
| single-reviewer reviewed sample | diagnostic/error analysis only |

## Paper-ready wording

The following wording is safe to use as a starting point:

```text
We construct ground truth from reproduction evidence rather than from model
judgments or single-reviewer labels.  Each record must contain a confirmed
local reproduction, runtime marker, runtime stub/monkeypatch observation,
source-level trace, or boundary/reachability proof.  We then separate
security-sensitive behavior ground truth from vulnerability ground truth:
behavior ground truth requires a reproduced security-relevant path, whereas
vulnerability ground truth additionally requires confirmed impact and a
trust/authentication boundary.  This distinction prevents intended features,
guarded helper utilities, syntax validators, and source-only traces from being
misreported as vulnerabilities.

In the current snapshot, the reproduction-confirmed ground truth contains 22
security-sensitive behavior cases across 13 repositories.  Only one case is
classified as vulnerability ground truth, one case remains a pending
disclosure/upgrade candidate, and 20 cases are explicitly retained as guarded
not-vulnerability or negative-control cases.  No human single-reviewer labels
or model labels are used to construct this ground truth.
```
